# Offline assistant startup investigation

Goal: investigate the intermittent offline-assistant failure, check post-merge CI, fix confirmed defects and retain all existing checks. Paid provider execution stays disabled. Acceptance: a regression fails before its fix and passes after; bounded diagnostics retain useful failure stages without secrets; existing native, assistant and embedded assertions pass without increased deadlines, retries or relaxed gates.

PR7 merged as `45c19a610f491e7eb7f814da412e970e3da541f4`. Its [post-merge Windows/native and Linux sanitizer run](https://github.com/siddsan7/ToneScope/actions/runs/39345914854) passed. That run describes merged main before these fixes; it is not CI evidence for the current working tree.

## Confirmed findings and changes

- Offline `host.ts` imported `gateway-provider.ts` for its configuration schema, which eagerly initialized the live SDK even when live mode was disabled. A source-host startup regression that denies the unused SDK failed on the old code and passes after the change, within the existing eight-second budget. The unchanged schema now lives in `live-policy.ts`; `gateway-provider.ts` reexports it, and host loads the provider dynamically only after the existing live-mode/configuration/credential checks. This removes a demonstrated offline startup dependency; it does not prove why the old nightly failed.
- `AssistantIntegration.inc` previously replaced every bridge error with the same service-setup message. Historical logs therefore cannot distinguish handshake, preparation or HTTP failures. Native errors now expose only allowlisted fixed categories or validated three-digit HTTP status codes. Untrusted exception strings, paths and bearer details stay hidden. Native tests cover redaction and a real broker HTTP403 response.
- The UI probe previously kept polling for a proposal after the assistant had already entered an error state, producing a later generic timeout. It now fails immediately with the bounded native diagnostic. The verified-proposal condition and45000ms deadline remain; the native8000ms startup and65000ms HTTP settings are unchanged. Two new regressions run alongside all five existing discovery checks in CI.

## Reproduction limits

Thirty pre-SDK-fix native bridge repetitions on the diagnostic build and eight full embedded workflows against an unchanged copied package passed. The historical proposal failure was not reproduced. These are repeated software checks, not proof that an intermittent failure is eliminated.

Initial probes against the exact executable already open in the user's normal window could not expose a debug endpoint. A fresh-path copy with the same seven manifest-owned payload hashes passed8/8. The live executable had an active EXE-adjacent WebView2 profile. This supports a separate shared-profile startup conflict. No user window was closed; no live profile is included in the test copy. Restricted-environment and stalled-shell attempts are retained separately and are not counted as assistant request failures.

It noted that source SDK-isolation tests alone do not verify packaged lazy initialization; final checks therefore exercise a fresh actual broker bundle/package.
